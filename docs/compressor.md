# Офлайн-компрессор под RTX 3080 12 ГБ

Стык со схемой: [schema.md](schema.md). Адрес куска тот же: `(слой, матрица, row_tile, col_group)`. Здесь — как из HuggingFace safetensors получить файл, **не загружая 14B/32B BF16 целиком**.

Компрессор работает на той же карте, что и инференс. 8B BF16 ≈ 16 ГБ, 14B ≈ 28 ГБ, 32B ≈ 64 ГБ — в 12 ГБ не влезает ни одна. Влезает **одна матрица** (макс. ~0,3 ГБ Linear, ~1,6 ГБ embed/lm_head).

---

## Рекомендация одной фразой

**v1:** стрим тензор за тензором → **NF4, группа 64, без калибровки** (кодек A). Параллельно можно писать **книжку 2×8, группа 8, k-means по MSE весов** (кодек B, M=2). 8B на 3080 — **20–40 минут**, не два часа. 32B той же процедурой — **1,5–3 часа**. Полный GPTQ/AQLM в v1 не обещаем.

Калибровка (AWQ/GPTQ/fine-tune книжки) — отдельный проход, когда v1 уже гоняет ядро.

---

## 1. Что влезает: одна матрица, не модель

Типичные Linear в BF16 (одна матрица на GPU, остальные на диске):

| Модель | Q | gate / up | down | embed / lm_head |
|---|---|---|---|---|
| Llama-3 8B (d=4096, ff=14336) | 34 МБ | **117 МБ** | 117 МБ | **1,05 ГБ** |
| Qwen2.5 14B (d=5120, ff=13824) | 52 МБ | 142 МБ | 142 МБ | ~1,3 ГБ |
| Qwen2.5 32B (d=5120, ff=27648) | 52 МБ | **283 МБ** | 283 МБ | **1,56 ГБ** |

Пик весов — не FFN, а `embed_tokens` / `lm_head`. Всё равно <2 ГБ. Нормы (RMSNorm) не квантуем, они килобайты, оставляем BF16.

Убийца не W, а **кэш активаций** при калибровке. 128 последовательностей × 2048 токенов:

| Что | 8B, d_in=4096 | 8B, down d_in=14336 | 32B, down d_in=27648 |
|---|---|---|---|
| X в FP16, всё сразу | 2,1 ГБ | **7,5 ГБ** | **14,5 ГБ** |
| Гессиан H=XXᵀ, FP32 | 67 МБ | 822 МБ | **3,1 ГБ** |
| Только средние \|x\| по каналу | 8 КБ | 28 КБ | 54 КБ |

Отсюда таблица «можно ли калибровать на 12 ГБ»:

| Метод | 8B | 14B | 32B |
|---|---|---|---|
| Weight-only NF4 / INT4 / k-means | да, минуты | да | да, часы |
| Imatrix (накопить x² по каналу, X батчами на CPU) | да | да | да |
| AWQ: только s_X + сетка α, X кусками | да | да | да, если слой за слоем |
| AWQ/GPTQ: держать весь X слоя на GPU | впритык / нет | нет | нет |
| GPTQ: модель на CPU, слой на GPU, H += X_bᵀX_b | да, ~1 ч | да, 2–4 ч | да, ночью, если не копить квант на GPU |
| AQLM: beam + block fine-tune | нет как v1 | нет | нет (у авторов 7B ≈ сутки на A100) |

GPTQ на 12 ГБ для 8B — **да**, если не делать `from_pretrained` всей модели в VRAM (это классический OOM AutoGPTQ). Рецепт TheBloke: веса на CPU/диске, на карте только текущий слой + гессиан. 32B: H для down_proj 3,1 ГБ + Cholesky ещё ~2–3 ГБ — влезает, **если на карте больше ничего нет**.

AWQ легче GPTQ: не гессиан, а пер-канальные магнитуды и сетка из ~20 значений α ([Lin et al., MLSys 2024](https://arxiv.org/abs/2306.00978)). Кэш X всё равно нужен на время поиска шкалы — его стримят батчами или берут подмножество токенов (128–512).

## 2. v1, который точно доедет за <2 ч на 8B

Один проход по диску. Калибровки нет.

```
для каждого шарда из model.safetensors.index.json:
  открыть файл (mmap / safe_open), LRU = 1 файл
  для каждого тензора в шарде:
      если RMSNorm / bias / rotary → скопировать BF16 как есть
      если nn.Linear / embed / lm_head:
          прочитать ТОЛЬКО этот тензор → GPU
          кодек A: NF4-g64
          кодек B (опционально, тот же W): residual k-means M=2
          дописать блоб в model.chr
          удалить W, empty_cache()
```

Не вызывать `AutoModelForCausalLM.from_pretrained` без `device_map` + пустых весов. Не собирать `state_dict`. Читать через `safetensors.safe_open` / `get_slice` по имени из `index.json`.

**Почему NF4, не INT4-RTN и не GPTQ.** QLoRA: NF4 — сетка под N(0,σ), на весах лучше FP4/INT4 без калибровки ([Dettmers et al., 2023](https://arxiv.org/abs/2305.14314)). Разница с AWQ/GPTQ на 4 битах — обычно **+0,2–0,5 PPL** к BF16 у всех трёх; для первого чата NF4 хватает. Калибровка не ускоряет ядро, только качество.

**Почему книжка сразу M=2, не M=1.** M=1, B=8, g=8 — это **1 бит/вес**. Даже полный AQLM 1×8 на Llama-2-7B даёт WikiText **7.85** при FP16 **5.12**. Без обучения книжки будет хуже. M=2 → 2 бит/вес, это как раз этап B схемы и формат AQLM `2x8` ([Egiazarian et al., 2024](https://arxiv.org/abs/2401.06118)).

Время v1, 3080, NVMe:

| Шаг | 8B | 14B | 32B |
|---|---|---|---|
| Чтение safetensors + NF4 | 5–15 мин | 10–25 мин | 20–45 мин |
| + k-means M=2, GPU | +15–25 мин | +30–50 мин | +1–2 ч |
| Итого v1 оба кодека | **20–40 мин** | ~1 ч | **1,5–3 ч** |

## 3. Кодек A — group-wise NF4

Как bitsandbytes / QLoRA, группа по **входу** (ось K), чтобы тайл `(row_tile, col_group=8)` брал одну и ту же шкалу на 8 соседних весов.

**Шаги на матрице W ∈ R^{n_out × n_in}:**

1. `n_in` должно делиться на 64 (если нет — паддинг нулями, в заголовке исходный `n_in`).
2. Нарезать W на группы `[n_out, n_in/64, 64]`.
3. `s = max(|g|)` по последней оси. Если s=0 → s=1.
4. `u = g / s`, клип в [−1, 1].
5. Каждое u → ближайший уровень **фиксированной** таблицы NF4 (16 квантилей N(0,1), как в QLoRA; книгу не учим).
6. Упаковать два ниббла в байт. Расклад: `[n_out, n_in/2]` uint8, row-major. Тайл 64×8 весов = 64×4 байт, непрерывный по строке кусок.
7. Шкалы: `[n_out, n_in/64]` FP16.
8. Double-quant шкал (ещё −0,4 бит в QLoRA) в v1 **не делаем** — экономия копеечная, ядро сложнее.

Асимметричный INT4 + zero-point (GPTQ/AWQ-pack) — тот же контейнер, другие `codec` и опциональное поле `zeros`. Ядро одно: ниббл → dequant(`scale`, `zero`, уровень).

**Калибровка потом, не вместо.** Если память позволяет (8B — да):

- **AWQ-lite:** прогнать 128×512 токенов слой за слоем; на CPU копить `s_X[j] = mean(|X[:,j]|)`; сетка α ∈ {0, 0.05, …, 1}; выбрать α, минимизирующий ‖X Wᵀ − X Q(s⊙W)ᵀ‖ на **подвыборке** X (не на всех 256k токенах). Затем обычный NF4/INT4 по уже умноженным каналам. Обратную шкалу вшиваем в следующую норму / не храним отдельно, как в AWQ.
- **GPTQ:** H = 2XᵀX накопительным GEMM батчами (`H.addmm_(Xb.T, Xb)`), Xb сразу выбрасывать. Дальше столбец за столбцом с поправкой по H⁻¹ ([Frantar et al., 2022](https://arxiv.org/abs/2210.17323)). На 3080 для 8B влезает. Для 32B down_proj — только этот рецепт, без кэша X.
- **Не делать** `desc_act` / act-order в v1: ломает последовательный доступ тайла по K.

## 4. Кодек B — книжка, группа 8

Формат как AQLM / additive quantization ([Babenko & Lempitsky, 2014](https://www.cv-foundation.org/openaccess/content_cvpr_2014/html/Babenko_Additive_Quantization_for_2014_CVPR_paper.html); [Egiazarian et al., 2024](https://arxiv.org/abs/2401.06118)):

```
группа из 8 весов ≈ C₁[i₁] + C₂[i₂]     # M=2
C_m ∈ R^{256 × 8}                       # B=8
индексы i — uint8
```

Бит/вес = M·B / 8 = **2,0** при M=2. Книга на матрицу: 2×256×8×2 Б = 8 КБ. На слой 7 матриц ≈ 56 КБ. В smem ядра — те же 4–8 КБ на матрицу, что в схеме.

### 4.1. v1: residual k-means, только MSE(W)

Без гессиана, без X. Это **инициализация** AQLM (residual k-means, Chen et al. 2010), без их beam search и block fine-tune.

```
векторы V ← W.reshape(n_out * n_in/8, 8)     # не копировать лишний раз, view
R ← V
для m = 1..M:
    C_m, idx_m ← k-means(R, k=256, iters=20)
    R ← R − C_m[idx_m]
записать C[0:M], idx[0:M]
```

Lloyd на GPU:

1. Книга 256×8 в smem / кэше (4 КБ).
2. Assignment **чанками** по 256k–1M векторов: `dist = ‖x‖² + ‖c‖² − 2 x Cᵀ` (GEMM), argmin.  
   **Нельзя** материализовать `(N, 256, 8)` — для жирной матрицы это ~60 ГБ и мгновенный OOM.
3. Update: сумма и счётчик по 256 корзинам (два прохода или `index_add`). Пустые кластеры — респлит самого толстого.
4. 15–25 итераций. k-means++ только на подвыборке 64k векторов.

Mini-batch k-means ([Sculley, 2010](https://www.eecs.tufts.edu/~dsculley/papers/fastkmeans.pdf)) — запасной путь, если полный Lloyd вдруг упрётся; качество чуть хуже.

### 4.2. Сколько стоит одна 4096×14336 на 3080

- Векторов: 4096×14336 / 8 = **7,34M**, dim=8, k=256.
- Один assignment = GEMM (7,34M × 8) × (8 × 256) ≈ **30 GFLOP** + argmin.
- 3080: 29,8 TFLOP/s FP32, 912 ГБ/с. Теория: **~1 мс** compute, **<1 мс** память.
- Практика с оверхедом Python/sync: **1–5 с** на матрицу при нормальном CUDA k-means (faiss-gpu / свой кернел). 20 итераций + k-means++.
- M=2: ×2, плюс вычитание → **3–10 с**.
- sklearn на CPU: **2–10 мин** на ту же матрицу. На 8B это уже часы — CPU-only не наш v1.

8B ≈ 7×10⁹ весов Linear ≈ 120 таких «жирных эквивалентов». GPU k-means M=2: 120×6 с ≈ **12 мин** чистого счёта, с I/O **15–25 мин**.

32B ×4 по параметрам: **1–2 ч** k-means. Ночь не нужна, ночь — запас на калибровку.

Полный AQLM (beam + fine-tune книжек на активациях): 7B ≈ **1 день на A100**, 70B ≈ 10–14 дней на одной GPU ([AQLM, app. D](https://arxiv.org/abs/2401.06118)). На 3080 это не overnight.

### 4.3. Калибровка книжки, если память позволит

Порядок по цене:

1. **Инициализация как в §4.1** — всегда.
2. **2–3 прохода Lloyd уже с весом канала** `w_j = mean(x_j²)` (imatrix / диагональ Фишера, как SqueezeLLM). X не храним: один forward слой за слоем, на CPU `acc[j] += x_j²`, потом weighted k-means. Влезает в 12 ГБ на 8B/14B/32B.
3. **Послойный MSE(XW)**: зафиксировать индексы, выучить C из `min ‖X (W − decode(C,idx))ᵀ‖` — это линейная задача по C. X батчами с CPU. На 8B — да. На 32B down_proj X тяжёлый: батч 1–2 последовательности.
4. Beam + block fine-tune AQLM / GPTVQ ([van Baalen et al., 2024](https://arxiv.org/abs/2402.15319)) — не v1.

## 5. Как не поймать OOM

Жёсткие правила компрессора:

1. **Стрим с диска.** Открыт один шард. Прочитан один тензор. После кодека — `del W; torch.cuda.empty_cache()`.
2. **Модель целиком не жить ни в VRAM, ни обязательно в RAM.** 32B BF16 = 64 ГБ host RAM; если RAM меньше — только mmap шарда, не `load_state_dict`.
3. **Слой за слоем для калибровки.** Загрузить layer i (BF16), прогнать батч, активацию **сразу на CPU** (pin memory), удалить layer i, загрузить i+1. Префикс уже в кванте можно держать на диске и подгружать INT4, если нужен «как у GPTQ» накопленный вход; для v1 калибровки нет, вопрос не стоит.
4. **X не целиком.** Гессиан: `H += X_bᵀ X_b` по 1–4 сиквенсам. AWQ search: случайные 1–2k токенов, не 256k.
5. **Квант сразу на диск.** Не копить сжатую модель в VRAM во время сжатия (на 32B это ~8 ГБ и гессиану уже тесно).
6. **k-means чанками.** См. §4.1.
7. **embed / lm_head по отдельности.** Если 1,6 ГБ + книга + чанк дистанций > комфорта — считать NF4/k-means **по полосам** строк (например 4096 строк), книга общая: первый проход накопить на подвыборке строк, второй — присвоить индексы.
8. **Не держать два BF16-слоя** «на всякий prefetch» во время сжатия. Prefetch — для рантайма, не для компрессора.

Пик v1 на 32B, грубо: CUDA context ~0,5 ГБ + lm_head 1,6 ГБ + чанк дистанций k-means (1M×256×2 ≈ 0,5 ГБ) ≈ **3 ГБ**. Запас огромный.

## 6. Формат файла `.chr` (CHR0)

Как safetensors: JSON-заголовок + сырые блобы. Ядро читает по offset, не парсит всю модель.

```
offset 0        uint64  header_nbytes     # длина JSON, little-endian
offset 8        UTF-8   header_json
offset 8+N      pad to 64 bytes
дальше          payloads, каждый выровнен на 64
```

### 6.1. Заголовок

```json
{
  "magic": "CHR0",
  "version": 1,
  "arch": "llama",
  "hidden_size": 4096,
  "intermediate_size": 14336,
  "num_layers": 32,
  "vocab_size": 128256,
  "tile": { "row": 64, "col_group": 8 },
  "tensors": {
    "model.layers.0.self_attn.q_proj": {
      "layer": 0,
      "kind": "q",
      "codec": "nf4",
      "shape": [4096, 4096],
      "group_size": 64,
      "data":  [4096, 8200],
      "scale": [8200, 16400]
    },
    "model.layers.0.mlp.down_proj": {
      "layer": 0,
      "kind": "down",
      "codec": "vq",
      "shape": [4096, 14336],
      "group_size": 8,
      "n_codebooks": 2,
      "codebook_bits": 8,
      "codebook": [20000, 28192],
      "index": [28192, 200000]
    },
    "model.norm.weight": {
      "kind": "norm",
      "codec": "bf16",
      "shape": [4096],
      "data": [200000, 208192]
    }
  }
}
```

Поля `data` / `scale` / `zero` / `codebook` / `index` — это `[start, end)` **от начала файла**, не от конца заголовка. Так проще `mmap`.

`kind`: `q k v o gate up down embed lm_head norm other`.

`codec`: `bf16` | `nf4` | `int4` | `vq`.

В одном файле могут жить оба кодека (A на 8B-прогоне, B на тех же именах с суффиксом или отдельный `.chr`). Для сравнения ядер удобнее **два файла** из одного прохода: `model.nf4.chr` и `model.vq2.chr`.

### 6.2. Расклад блобов

**nf4 / int4**

- `data`: uint8, форма `[n_out, n_in/2]`. Байт `data[r, c]` = nibble `W[r, 2c]` в младших 4 битах, `W[r, 2c+1]` в старших. Уровень 0..15 — индекс в таблице NF4 или смещённый INT4.
- `scale`: FP16, `[n_out, n_in/group_size]`, group_size=64.
- `zero`: опционально FP16 той же формы (для `int4` асимметричного). У NF4 нет.
- Тайл `(row_tile=i, col_group=j)`: строки `[64i, 64i+64)`, столбцы весов `[8j, 8j+8)` → байты `data[64i:64i+64, 4j:4j+4]`, шкала `scale[64i:64i+64, floor(8j/64)]`.

**vq**

- `codebook`: FP16, `[M, 256, 8]`.
- `index`: uint8, `[n_out, n_in/8, M]`. Для M=2 два байта на группу.
- Тайл `(i, j)`: `index[64i:64i+64, j, :]` → gather из книги, сложить M векторов по 8, это и есть 64×8 BF16 в регистрах.

**bf16:** сырой little-endian, как в safetensors.

Имена тензоров — HuggingFace (`model.layers.{L}.mlp.down_proj.weight` без суффикса `.weight` или с ним — зафиксировать: **без `.weight`**, bias если есть — `.../bias`, codec `bf16`).

Конца файла: ничего магического. Длина = max(end). Контрольная сумма в v1 не обязательна; если нужна — `sha256` всего файла в соседнем `model.chr.sha256`.

## 7. Минимально живое качество: NF4 + k-means 256 без гессиана

**NF4 без GPTQ — да, для первого теста ок.** Это штатный 4-бит QLoRA. На Llama-классе 7B/8B WikiText обычно в пределах ~0,3–0,6 от BF16, чат связный. Хуже AWQ/GPTQ на том же бите, но не «сломанная модель». Это правильный калибр: ядро и формат, не охота за 0,1 PPL.

**K-means 256, g=8, без калибровки — ок как диагностика этапа B, не как чат на 32B.**

- Полный AQLM 2×8 (с обучением на X) на Llama-2-7B: WikiText **7.61**, с доп. fine-tune **6.57**, FP16 **5.12** (таблица 12 статьи).
- Residual k-means — только их init. Без шагов 2–3 из §4.3 будет заметно хуже 7.61. Ожидание: модель ещё говорит предложениями, тупеет, иногда плывёт. Этого достаточно, чтобы увидеть, что ядро книжки едет и PPL не 50.
- M=1 (1 бит) в первый прогон **не класть** как цель качества: даже обученный 1×8 уже 7.85, вес-only будет мусором.
- Гессиан GPTQ на книжку (GPTVQ) в v1 не нужен: он дорогой и не отвечает на вопрос «съест ли формат 12 ГБ».

Практический критерий приёмки v1:

1. 8B NF4: WikiText не уезжает в космос (ориентир: не хуже +1,0 к BF16). Чат на 10 вопросов не бредит.
2. 8B VQ 2×8 weight-only: PPL снять и записать, чат — «жив / мёртв». Если мёртв — не чинить книжку гессианом, пока нет imatrix.
3. Ядро vs llama.cpp Q4 на том же 8B — отдельная приёмка, компрессор тут ни при чём.

## 8. Путь к 32B за ночь

Одна карта, один диск, без многоGPU.

| Ночь | Что гоняем | Зачем | Укладывается в 12 ГБ? |
|---|---|---|---|
| Сначала (вечер) | v1 NF4 на 8B, прогнать чат + ядро | калибр конвейера | да |
| Тем же вечером | v1 VQ 2×8 на 8B, снять PPL | понять ущерб книжки без X | да |
| Ночь 1 | v1 NF4 + VQ на **32B**, те же флаги | файл для этапа B схемы | да, 1,5–3 ч |
| Ночь 2, если чат 2-бит плохой | imatrix: 128×512, слой за слоем, X на CPU; пересчитать k-means с весом канала | дешёвая калибровка, как llama.cpp imatrix / диагональ SqueezeLLM | да |
| Ночь 3, если 4-бит 14B/32B важен | AWQ-lite на 14B, потом 32B | качество этапа A без гессиана | да при стриме X |
| Когда-нибудь | GPTQ-stream на 8B, сравнить с NF4 | стоит ли таскать H | да на 8B; 32B — да, но дольше ночи, если неоптимально |
| Не обещаем на 3080 | полный AQLM / PV-Tuning | SOTA 2 бит | нет по времени |

32B NF4 ≈ 16 ГБ / 4 = 4 ГБ весов? Нет: 32B × 0,5 байт ≈ **16 ГБ**, на 12 ГБ не влезет. Этап A на 32B — не цель схемы (схема: 32B в **~2 битах** ≈ 8 ГБ). Ночью имеет смысл писать **VQ 2×8 на 32B**, NF4 на 32B — только если потом offload. 14B NF4 ≈ 7–8 ГБ — влезает, это этап A.

Итого overnight 32B: **один прогон §2 с кодеком B**. Утром есть `model.vq2.chr` ~8 ГБ. Если PPL страшный — ночь 2 с imatrix, не GPTQ.

## 9. Порядок реализации (без простыни кода)

1. Читалка `index.json` + `safe_open`, печать имён/форм, пик RSS/VRAM. Проверка: 32B индекс проходит без загрузки весов.
2. Писалка CHR0: заголовок в память, блобы append, в конце переписать JSON и `header_nbytes`.
3. Кодек A на одной `4096×4096`, сверка decode vs W (MSE, max err).
4. Прогон 8B → `*.nf4.chr`, замер времени и пика VRAM (должно быть <4 ГБ).
5. Кодек B: чанковый k-means на одной `4096×14336`, замер секунд — сверка с §4.2.
6. 8B VQ, PPL. Потом 32B VQ ночью.

Зависимости v1: `torch`, `safetensors`, опционально `faiss-gpu`. Без transformers-модели в памяти.
