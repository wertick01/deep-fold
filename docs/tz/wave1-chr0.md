# ТЗ агенту 1: контейнер CHR0 и стрим safetensors

## Роль

Ты продумываешь **только** бинарный контейнер `.chr`, JSON-заголовок, чтение HuggingFace safetensors (один файл и шарды через `model.safetensors.index.json`) и то, как Go будет стримить тензор за тензором **на CPU**. Кодеки NF4/VQ не проектируй — только слоты под их блобы.

Это **не** инференс и **не** GPU. Цель среза: скачать модель позже, сжать, разжать, сравнить с оригиналом на диске.

## Зафиксировано (не спорь)

- Магия контейнера: `CHR0`, `version: 1`.
- Расклад как safetensors: `uint64le header_nbytes` + UTF-8 JSON + pad до 64 + блобы, каждый pad до 64.
- Офсеты `[start, end)` от **начала файла**.
- `codec`: `bf16` | `nf4` | `vq`. `int4` в JSON разрешён, в этом срезе не кодируем.
- Имена тензоров — как в HF, **без** суффикса `.weight`. Bias: `model.layers.0.self_attn.q_proj.bias`, codec `bf16`.
- `kind`: `q k v o gate up down embed lm_head norm other`.
- В одном `.chr` — один кодек для всех Linear/embed/lm_head; нормы/bias всегда `bf16`.
- Не держать модель целиком в RAM: один открытый шард, один тензор, сразу писать блоб, исходный буфер отпускать.
- Выход второй волны — пакеты Go без CGO. Спека должна быть реализуема на `encoding/binary` + `os.File`.

## Напиши файл `docs/spec/chr0.md`

До мелочей. Обязательные разделы:

1. Байт за байтом: что на offset 0, как считать pad, что если JSON невалиден, что если `header_nbytes` врёт, endian.
2. Полная JSON-схема заголовка (все поля, типы, обязательность). Пример на крошечной «модели» из 3 тензоров (q_proj 64×64, down 32×128, norm 64).
3. Алгоритм записи: как копить офсеты, когда переписывать JSON в начало (два прохода vs временный sidecar). Что делать, если JSON после блобов вырос и не влезает в зарезервированный слот. Выбери **один** способ и распиши.
4. Алгоритм чтения: mmap vs `ReadAt`; для Windows/WSL достаточно `ReadAt`. Как достать один тензор по имени.
5. Парсер safetensors: магия, header, `dtype` (`F32`/`F16`/`BF16`), `shape`, `data_offsets`. Как ходить по `index.json` (`weight_map`). Что делать с тензорами не-весов (inv_freq и т.п.): копировать `bf16` или пропускать? Выбери и обоснуй одной фразой.
6. Классификация тензора → `kind` + `codec` по имени (regex/суффиксы). Таблица.
7. Pad `n_in` до кратности 64 (NF4) или 8 (VQ): где хранить **логический** shape vs padded. Не придумывай второй shape в тайле ядра — для CPU-проверки блобы **row-major**, как в `docs/compressor.md` §6.2. Ampere fragment-major — не этот срез.
8. Пределы: максимальный JSON, максимальный тензор, пустой файл, 0 тензоров, дубли имён.
9. Контрольная сумма: в v1 файла нет; `verify` считает метрики сам.
10. Стык с кодеками: какие ключи обязательны у `nf4` (`data`,`scale`,`group_size`) и у `vq` (`codebook`,`index`,`n_codebooks`,`codebook_bits`). Точные dtypes и shapes блобов, без формул квантования.
