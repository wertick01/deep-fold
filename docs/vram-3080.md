# VRAM budget: RTX 3080 12 GB = exactly 12288 MB

The unit is **MiB** (`1024²` bytes). The card is advertised as 12 GB; in CUDA that is **12288 MB**.

Measured (not this table; live CSVs in [`runs/`](runs/)): Qwen2.5-14B BF16 after
load gives ~28 172 MiB of weights and ~28 270 MiB `torch` — matching the full
BF16 row below. `nvidia-smi` saturates at 12288. NF4 14B stays on the card
(~7 483 MiB of weights). internlm2.5-20B was not run.

Counted from real `config.json` (Llama-3.1-8B — NousResearch / unsloth mirror, matched HF safetensors **8 030 261 248** weights; Qwen2.5 — official repos). There is **no** Llama-3.1 in the 32B class (there are 8B / 70B / 405B) — we take **Qwen2.5-32B**.

KV per token: `2 × L × n_kv × head_dim × sizeof`. 14B and 32B share `hidden` and GQA; 32B is more expensive because of 64 layers (and a wide MLP — but MLP is not in KV).

The Qwen model card rounds; the budget uses the sum over shapes.

## Schema rules (these change the peak)

1. **There is no layer scratch in HBM.** We do not keep a BF16 layer matrix (for 8B down/gate ≈ 436 MB, for 32B ≈ 975 MB — that would eat Huffman-8B and 32B-2bit).
2. In **smem** only the ring: **2 compressed tiles + 1 unpacked**. Ampere block ≤ 99 KB.
3. CUDA context is planned at **768 MB** (the middle of the requested 0.5–1 GB). Sensitivity: ±256 MB to leftover.
4. Decode activations `b=1`: residual + ping-pong hidden + softmax — **48 MB** HBM, not a layer.
5. Allocator reserve **64 MB**.
6. **Fixed overhead = 768 + 48 + 64 = 880 MB** on every row below.

A 64×64 tile in smem (not in the 12288):

| Codec | 2 compressed | 1× BF16 | smem total |
|---|---:|---:|---:|
| INT4 4.5 bit | 4608 B | 8192 B | 12.5 KB |
| 2-bit | 2048 B | 8192 B | 10.0 KB |
| Huffman ~11 bit | 11 264 B | 8192 B | 19.0 KB |
| codebook 2×8 (256×8 BF16 × 2) | | | +8 KB, fits |
| codebook 1×16 (65536×8 BF16) | | | **1024 KB — HBM only**, slice it in smem |

## Codecs

**INT4 groupwise.** Group 32, FP16 scale, no zero-point: `4 + 16/32 = 4.5 bit/weight`. Norms and QKV-bias — BF16 (≤ 2.2 MB). Embed and lm_head are INT4 too — otherwise one Qwen embedding pair is already **2970 MB** BF16.

**2-bit additive (AQLM).** Group `g=8`. Linear indices: exactly **2 bit/weight**.
- Codebook **1×16**: `1 × 65536 × 8 × 2 = 1.00 MB` per matrix × 7 matrices × L.
- Codebook **2×8**: `2 × 256 × 8 × 2 = 8 KiB` per matrix (this is what we actually put in smem).
- Scales: FP16 per output channel (`d_out × 2`).
- Embeddings in AQLM papers are often left BF16; on 12 GB for 32B that almost kills context. **Baseline plan: embed+lm_head INT4 4.5 bit.** The “published BF16 embed” row is separate.

**BF16 Huffman ~11 bit (DFloat11).** We take **11.0 bit/weight** on linears + embeddings. Official Llama-3.1-8B-Instruct: 16.06→10.90 GB₁₀ = **10 395 MB**, **10.85 bit**. Huffman tables ≈ 4 MB. **Only 8B has a chance.** 14B/32B — no, even without KV.

| Model | Weights @11.0 bit | Leftover | 512 FP16 | 2048 | 4096 | 8192 FP16 | 8192 Q8 | max FP16 / Q8 |
|---|---:|---:|---|---|---|---|---|---|

| 32B | **42 968** | **−31 560** | no | no | no | no | no | no |

8B Huffman **fits only because there is no layer scratch**. Official DFloat11 decompresses a block into HBM (~400–500 MB on 8B) — then leftover drops to ~370–470 MB, and 4k FP16 is already doubtful. Our schema forbids that.

8k FP16 on 8B Huffman: on the edge. With CUDA=768 and reserve 64 — no. With CUDA≤512 and no reserve — yes. Practical: **Huffman-8B → KV Q8, context 4–8k**.

14B/32B Huffman on 12 GB are not considered.

| Buffer | 8B | 14B | 32B |

| hidden ×2 BF16 | 16 KiB | 20 KiB | 20 KiB |
| gate+up BF16 (if both are materialized) | 56 KiB | 54 KiB | 108 KiB |

| RoPE cos/sin at 8k | ~4 MB | ~4 MB | ~4 MB |

The peak is kilobytes + a small workspace. **48 MB** is headroom for kernels, not for a layer.

## PCIe — a backup hatch only

32B 2-bit **does not overflow** 12288 with embed INT4 and no layer scratch. Offload is not needed.

It only makes sense if simultaneously: BF16 embeddings were left, a fat CUDA context, and/or HBM-scratch suddenly appeared — or if someone insists on INT4-32B (−6169 MB).

Estimate if we still spill **20% of layers** to RAM and shuttle them every token over PCIe 4.0 ×16 (**32 GB/s** theoretical, ~26 GB/s actual):

32B 2×8, layer ≈ **123.4 MB** (codes + codebook). 20% × 64 = 12.8 layers → **1579 MB/token**.

| | |
|---|---|
| PCIe 32 GB/s | 51.8 ms → **19.3 tok/s** ceiling |
| PCIe 26 GB/s | 63.7 ms → **15.7 tok/s** |
| HBM 80% of layers @ 912 GB/s | 6318 MB / 7.3 ms |
| Sequential GPU+PCIe | **16.9 tok/s** |
| Full overlap (PCIe hides GPU) | still **19.3 tok/s** — nothing to hide, PCIe is 7× longer |

This is streaming weights onto the GPU (like `-ngl`). Computing 20% on CPU is worse still: GEMV ~6.4B weights on a 20–40 GB/s CPU bus → 160–320 ms, **3–6 tok/s**.

INT4-32B over PCIe: layer ≈ 16740/64 = 261.6 MB, 20% = 3348 MB/token → **9.5 tok/s** theoretical at 32 GB/s. Worse than resident 2-bit.

## What is not included / assumptions

- Prefill peak (long prompt) is larger than decode: attention scores and activations grow as `b × s`. The budget is **decode b=1**.
- PagedAttention: a few percent.
- KV Q8 in the summary = exactly 8 bits; group scales ≈ ×1.0625.
- CUDA 768 MB is not a measurement on this card; after the first custom kernel, remeasure `nvidia-smi` on an empty context.
- 2-bit embeddings without a codebook would save another 313 / 464 / 464 MB on 8/14/32B relative to INT4-embed.

## Practical order on a 3080

1. **8B INT4** — caliber (≥10 tok/s easily; llama.cpp Q4 already 80–110).
2. **14B INT4** — working chat, 8k FP16 with ~1.9 GB headroom.
3. **8B Huffman** — only if bit-exact BF16 is needed; keep context Q8, do **not** write a layer to GDDR.
4. **32B 2-bit 2×8**, embed INT4 — the “large model on 12 GB” target; 8k FP16 leftover **1070 MB**.
5. Do not plan PCIe until 32B 2-bit starts overflowing because of BF16 embeddings or HBM-scratch.
